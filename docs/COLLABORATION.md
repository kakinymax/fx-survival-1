# スレッド間の作業共有

リポジトリ: https://github.com/kakinymax/fx-survival

文書は方針の共有、Issueは担当と進行状況、PRは実際の変更の共有に使う。別スレッドのチャットや未コミットのファイルは自動で共有されない。

## 最新状態を見る場所

- [open Issues](https://github.com/kakinymax/fx-survival/issues?q=is%3Aissue%20is%3Aopen): 予定、作業中、検証中、引き継ぎ、ブロック中。
- [open PRs](https://github.com/kakinymax/fx-survival/pulls?q=is%3Apr%20is%3Aopen): draftも含めた変更中の範囲とブランチ。
- [main](https://github.com/kakinymax/fx-survival/tree/main): 統合済みコードと共有文書。
- [現在地](PROJECT_STATUS.md): 完了した機能や節目の要約。進行中の一覧の代用にはしない。

APIでは `GET /repos/kakinymax/fx-survival/issues?state=open` と `GET /repos/kakinymax/fx-survival/pulls?state=open` の全ページを確認する。Issue一覧にはPRも含まれるため、作業IssueとPRを区別する。検索は補助として使い、反映遅延がある検索結果だけで予約の有無を判断しない。

## 着手から共有まで

1. 最新mainを取得し、[AGENTS.md](../AGENTS.md)と依頼に関係する仕様を読む。古いチェックアウトに他スレッドの変更を上書きしない。
2. open Issues/PRsを読み、同じ依頼だけでなく、編集するファイルや機能の重なりを確認する。
3. 重複がなければ、既存の同じタスクIssueを使うか、[作業Issueテンプレート](../.github/ISSUE_TEMPLATE/task.md)で新規作成する。担当セッション、固有のブランチ、基準SHA、変更範囲、状態「作業中」を編集前に公開する。
4. 宣言後にもう一度一覧を確認する。同時に重なる作業が作られた場合はIssue番号の小さい予約を先に扱い、後から着手する側は範囲を分けるか引き継ぎを確認する。先行作業を上書きして進めない。
5. Issueに対応する固有ブランチで作業する。例: `ui/issue-12-order-layout`、`feat/issue-15-challenge`。別スレッドで同じブランチを使わない。
6. 変更が共有できる段階でコミット・pushし、draft PRを作る。IssueとPRを相互にリンクし、残りの作業・検証・最新SHAを記録する。

同じファイルでも独立した範囲に分けられるなら、両方のIssueに分担と統合順を記載して作業できる。別ファイルでも同じ相場計算などを変更する場合は先に分担を確認する。

## Issueに置く情報

| 項目 | 書くこと |
| --- | --- |
| 状態 | 予定 / 作業中 / 検証中 / 統合待ち / 公開待ち / 引き継ぎ待ち / ブロック中 / 完了 |
| 担当 | スレッドの用途とセッション識別子。同じGitHubアカウントでも区別できる名前 |
| 依頼・完了条件 | ユーザーが依頼した内容と、何ができれば完了か |
| 変更範囲 | 機能、ファイル・ディレクトリ、変更しない範囲 |
| ブランチ・基準 | ブランチ、着手時のmain SHA、現在のコミット、PRリンク |
| 次の作業 | 未完了項目、再現手順、既知の制約、引き継ぎに必要な情報 |
| 検証 | 実行した内容と結果。未実施・失敗・報告に基づく情報を分ける |
| 公開 | 未公開 / 対象外 / 公開済み。公開済みなら対象SHAとURL・成功確認 |
| 更新日時 | UTC等、タイムゾーン付き日時 |

長い会話の全文、実際のプレイヤーの個人情報、認証情報を貼り付けない。作業を引き継ぐために必要な事実と判断を残す。

## 再開・引き継ぎ・完了

- 中断時は、どこまでGitHubへ保存したか、次の具体的な作業、未実施の検証をIssue/PRに残す。
- 再開時は最新mainとIssue/PRを再確認する。他のスレッドが担当を引き継いでいれば、二重に再開しない。
- 長時間更新がないだけで予約を解除しない。先行担当の記録またはユーザーの指示に基づいて引き継ぎを記録する。機械的な予約期限は設けない。
- push・統合前に他の変更とmainの更新を確認する。履歴を強制上書きせず、必要な競合解消と関連箇所の確認を行う。
- 完了時はIssueを更新し、統合済みSHA、PR、検証、公開状態を残す。対象の完了条件が満たされてから完了扱いにする。
- mainへ統合された変更だけを統合済みと扱う。draft PR、閉じたが未統合のPR、未公開の版を本番と混同しない。

この方式は、全スレッドが確認・宣言することで重複を減らす運用であり、GitHubが編集を自動ロックする仕組みではない。予約を記録せずに進める作業、まだGitHubへ出していない別スレッドの作業は検出できない。

## 別スレッドの最初の指示

以下に作業内容を追記して渡せる。

```text
リポジトリ: https://github.com/kakinymax/fx-survival
最新mainを取得し、AGENTS.mdとdocs/PROJECT_STATUS.mdを読んでください。
open Issuesとdraftを含むopen PRsを確認し、重複する作業がなければ、
担当セッション・変更範囲・固有ブランチを作業Issueへ記録してから着手してください。
作業中・中断時・完了時の進捗と引き継ぎも同じIssue/PRへ保存してください。
今回の依頼: （ここに作業内容を記入）
```
